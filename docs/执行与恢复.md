# 后端执行、恢复与 Agent 权限

本阶段把真实接入流程接入持久化 LangGraph，并为 OpenHands 会话、队列投递和本地候选提交建立恢复机制。正式采集仍由人工发起，平台登记运行结果并等待审查。

## 使用前提

- 先运行 Alembic `0006_durable_execution`，再启动新版 API、worker 和 scheduler。
- 自动验证在 Linux 容器中执行，使用 Landlock 限制候选代码的文件访问。内核不支持时返回 `VALIDATION_SANDBOX_UNAVAILABLE`，不降级为无限制执行。
- 原有任务、报告、候选提交和人工审查保留。旧顺序 runner 的历史轮次没有原生图 checkpoint，恢复接口返回 `NATIVE_WORKFLOW_RUN_REQUIRED`；已有候选仍可登记人工运行、提交审查，后续修复采用新工作流。
- 前端现有任务、报告、日志和审查页面继续使用。新增暂停/取消接口可在 `/docs` 调用；本阶段没有新增前端控制按钮。

## 启动与升级

在 `D:\Project\Auto_spider` 执行：

```powershell
docker compose up -d mysql redis
docker compose build api worker openhands-agent-server
docker compose run --rm --no-deps api alembic upgrade head
docker compose up -d --no-build api worker openhands-agent-server scheduler
```

`scheduler` 只投递平台执行恢复、队列补偿和停止请求处理，每 30 秒检查一次；不调度正式岗位采集，也不监控招聘网站变化。它与 worker 共用镜像。

## 控制执行

以下路径前缀都是 `/api/v1/onboarding/tasks/{task_id}`。操作接口沿用 operator/admin 权限，查询接口沿用查看权限。

| 接口 | 方法 | 作用 |
| --- | --- | --- |
| `/pause` | POST | 请求当前轮次暂停；运行中的 Agent 确认暂停后记录 PAUSED |
| `/cancel` | POST | 请求停止当前轮次，保留已有文件与记录；取消后不能恢复该轮次 |
| `/resume` | POST | 续接已暂停、失败、超时或中断的原轮次 |
| `/retry` | POST | 重试失败节点，复用原 checkpoint、工作区和会话标识 |
| `/executions` | GET | 查询会话 ID、所属轮次、步骤、工作区、权限模式和错误 |
| `/logs` | GET | 按 `after` 游标读取持久化工作日志 |

操作请求体含 `client_request_id`，长度为 8–128 个字符。同一次请求重发时保持相同 ID。

```json
{"client_request_id":"operator-retry-20260930-001"}
```

人工等待状态应使用 `/manual-runs`、`/reviews` 提交结果；普通 resume 请求不能跳过人工运行或审查。`RUN_NOT_RESUMABLE`、`RUN_ALREADY_FINISHED` 和版本不匹配返回 HTTP 409。

暂停/取消在长时间 Agent 调用期间由控制循环处理；自动验证会终止对应子进程组。网站分析等有限时操作在节点边界响应控制请求。远端未确认停止时保留执行占用，避免另一任务同时写入同一平台工作区。

## 恢复机制

| 存储 | 保存内容 | 恢复作用 |
| --- | --- | --- |
| `graph_checkpoints`、`graph_writes` | LangGraph 状态、下一节点、待提交写入、人工中断 | 新 worker 加载原 `run_id` 继续 |
| `workflow_steps` | 已完成节点结果 | 图 checkpoint 写入前中断时，复用已提交的节点结果 |
| `execution_leases` | 平台资源、轮次、持有者、租约期限 | 同平台串行；原轮次接管过期租约 |
| `workflow_dispatches` | 事务内记录的待投递请求、投递状态和错误 | Broker 故障后重新投递；重复消息由租约和节点记录去重 |
| `agent_executions` | 稳定 conversation ID、prompt hash、权限、工作区、结果 | 重新连接原 OpenHands 会话，避免重复发送初始任务 |

Agent Server 的会话数据写入命名卷 `auto-spider-agent-state`。`OH_SECRET_KEY` 必须保持一致，才能恢复加密保存的会话配置。恢复既有执行时若远端会话消失，返回 `AGENT_STATE_MISSING`，不偷偷创建替代会话。

候选提交采用确定的 Git tree、父提交、提交时间和轮次标识。创建提交后、写数据库前中断，再执行会得到同一 SHA。本地分支格式为 `codex/candidate/<platform_key>/<run_id>`，整个发布路径不执行 push，也不合并主分支。

## 验证与自动纠错

网站分析完成后，平台先构建并校验 PlatformSpec，再生成代码。分页、接口方法、
字段选择器等结构不符合契约时，向只读 Agent 提供原始分析、结构化错误和 JSON Schema，
默认最多纠正 2 次（`MAX_SPEC_REPAIR_ATTEMPTS`）。纠错只允许修改草稿的
adapter/endpoints/fields/pagination/filters，不能改观察结论、身份或生成权限。
`offset` 与 `page` 模式均使用 `page_param`，该关联约束也输出到 JSON Schema。

网站分析的第一份 Agent 输出也经过顶层契约校验：必须是可解析 JSON 对象，包含
`observation`、`evidence_refs`、`spec_draft`，方法、请求参数、证据引用和观察枚举都要符合类型。
格式错误会最多重试 4 次；第一次允许浏览器取证，后续只读取本轮已保存证据，并使用新的只读会话
修正 JSON，不重复访问网站。超过次数记录 `ANALYSIS_RETRY_EXHAUSTED`，保留原始会话和错误上下文。

每轮纠错结果和证据单独保存，原始 `analysis.json` 不覆盖；重投和 worker 重启复用原轮次
的纠错结果，包括无效 JSON，避免重复消耗预算。超过上限保存明确的
`DISCOVERY_SPEC_INVALID`、具体字段错误及纠错次数，不把未通过的 Spec 当成可用代码。

worker 定时恢复还会检查历史 `RUNNING` 工作流：只有同时满足“超过执行租约、没有有效心跳、
没有活动 AgentExecution、没有有效 ExecutionLease”才标记为 `INTERRUPTED/STALE_EXECUTION`。
当前人工等待任务不会被改写；旧轮次的错误信息和时间保留，用户可以从任务历史中发起重试。

流程顺序是：生成文件 → 编译/pytest/Ruff/契约/业务/真实接口验证 → 汇报 → 判断是否可提交 → 本地候选提交 → 等待人工运行 → 等待人工审查。

验证失败先保存结果和失败包，再判断能否修复。代码、配置、字段、筛选与分页问题可以进入 AI 修复；环境/访问阻断、证据不足、权限越界需要明确汇报。缺失或未运行的验证项不能默认为通过。每次修复后重新验证并生成报告，耗尽预算后记录 `REPAIR_BUDGET_EXCEEDED`。

验证器只观察和记录候选工作区，不能替 Agent 修改采集器、TOML、fixture 或测试文件。Ruff、编译和测试命令均以检查模式运行；格式、导入排序和业务修复必须由 OpenHands Agent 在自己的修复轮次中完成。平台不会把验证器的自动改写冒充成 Agent 修复。

默认每个轮次最多修复 3 次；暂停、重试和重复投递不会重置该轮次计数。人工审查提出的新问题创建新的修复轮次，并绑定被审查的候选 SHA。

人工运行必须绑定当前候选。审查必须同时匹配 task、manual_run 和 candidate SHA。被替代候选的审查不能采纳新代码；PASS 会同时更新任务、候选采纳状态与 Spec 状态，记录实际审查人。

## Agent 能修改什么

- 编码会话开放 `CollectorReadTool`、`CollectorWriteTool`，可按配置使用受限的
  `CollectorBrowserTool`；网站分析禁止写文件，Spec 结构纠错仅开放读取已有证据。
- 写工具只允许该公司的 `collectors/<key>.py`、`config/platforms/<key>.toml`、`tests/test_<key>.py` 和 `tests/fixtures/<key>/*`，并受本次 Spec 白名单进一步限制。
- 路径穿越、绝对路径、`.git`、`.env`、符号链接和硬链接写入被工具拒绝。Agent 没有通用终端与无限制文件编辑工具。
- 自动验证在单独的受限子进程中执行；它能读取本次工作区及系统运行依赖，只能写临时目录，环境中不携带数据库和模型凭证。
- Agent Server 以只读方式挂载 Git 主仓库元数据及平台策略；证据目录可写，以保存浏览器取证，
  具体工具访问范围仍由当前任务策略限定。

有证据支持的 Spec 修改写入 `tests/fixtures/<key>/platform-spec.patch.json`，包含 `reason`、已有 `evidence_refs` 和 `patch`。允许的 patch 部分为 endpoints、fields、pagination、filters，每部分提供完整结构。后端重新做 Pydantic 校验、递增 revision 并重新计算 hash，不覆盖历史 JSON。identity、generation、normalization 和业务 validation 规则不由 Agent 改写。

spider-king 的规则随提示词加载。浏览器用于网站分析和证据采集，正式采集保持纯 Python HTTP。
导航、筛选后必须使用新快照；元素引用失效时，工具保留失败记录，并在动作预算内自动刷新一次
快照，返回 `BROWSER_STALE_REF` 和 `recovery`。Agent 必须重新选择目标，工具不会按旧引用盲目重试。
快照刷新成功仅表示可继续选目标，原操作仍是失败，日志显示 WARNING；恢复失败保持 ERROR。

会话由平台通过 Agent Server 的类型化接口创建并关闭自动标题生成，避免辅助标题请求与
仅支持流式输出的模型接口不兼容。SDK `ConversationErrorEvent.code/detail` 会完整脱敏保存，
日志页面分别显示轮次状态和日志连接状态；“日志同步正常”不等于业务执行成功。

## 配置

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| `EXECUTION_LEASE_SECONDS` | 60 | 平台执行占用的有效期 |
| `EXECUTION_HEARTBEAT_SECONDS` | 5 | 执行心跳间隔 |
| `EXECUTION_TIMEOUT_SECONDS` | 3600 | 一次 worker 执行调用的时间上限；人工等待已释放 worker |
| `AGENT_MAX_ITERATIONS` | 100 | OpenHands 单会话运行迭代上限 |
| `AGENT_POLL_SECONDS` | 2 | 远端状态及控制请求检查间隔 |
| `MAX_REPAIR_ATTEMPTS` | 3 | 当前轮次修复次数上限 |
| `MAX_SPEC_REPAIR_ATTEMPTS` | 2 | 生成代码前的接入规范结构纠错上限 |

## 验证依据

| 证据 | 验证内容 | 复现入口 |
| --- | --- | --- |
| `tests/test_durable_execution.py` | 新 runner 恢复 checkpoint、重复投递、修复预算、Spec revision、暂停/取消、Broker 故障 | `python -m pytest tests/test_durable_execution.py` |
| `tests/test_execution_boundaries.py` | 文件权限、本地提交幂等、审查版本绑定、空库及重复迁移、Linux 子进程隔离 | `python -m pytest tests/test_execution_boundaries.py` |
| `tests/test_discovery_recovery.py` | 多种 Spec 异常、证据范围、纠错预算、重启恢复、JSON Schema 与运行时分页约束一致 | `python -m pytest tests/test_discovery_recovery.py` |
| `tests/test_agent_error_recovery.py` | 标题请求关闭、错误正文脱敏、旧引用自动刷新及恢复失败保持错误 | `python -m pytest tests/test_agent_error_recovery.py` |
| `tests/test_analysis_response.py` | 分析 JSON 顶层字段、枚举、请求参数和 Markdown 输出边界 | `python -m pytest tests/test_analysis_response.py` |
| `tests/test_stale_run_recovery.py` | worker 消失后的僵尸工作流回收，保护有效租约和 Agent 执行 | `python -m pytest tests/test_stale_run_recovery.py` |
| `tests/agent_server_probe.py` | 真实模型调用受限工具、服务器重启后续接原 conversation ID | 容器内执行 create → 重启 Agent Server → resume |

最后一项是显式运行的集成检查，会调用配置的模型，不随默认 pytest 执行。结果存放在 `evidence/runtime-verification/`，使用独立 SQLite 数据库，不往业务任务表写测试任务。

```powershell
docker compose run --rm --no-deps api python -m tests.agent_server_probe create
docker compose restart openhands-agent-server
docker compose run --rm --no-deps api python -m tests.agent_server_probe resume
docker compose run --rm --no-deps api python -m tests.agent_server_probe read-only
```

对正在执行真实任务的环境，应等当前 Agent 调用结束后再进行服务器重启演练。
