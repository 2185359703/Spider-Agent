# 开发计划与验收

本文档把完整平台拆成可以逐步验收的开发阶段。阶段性开发是实施方式，不改变最终范围：URL 接入、AI 开发、自动验证与汇报、人工运行审查、广义代码纠错和候选提交闭环。

## 1. 交付分层

### 1.1 第一层：可运行平台

完成服务启动、任务创建、持久状态、报告展示、人工审查和证据索引。此层可接受人工导入的模拟运行包，不依赖真实 OpenHands Agent。

### 1.2 第二层：真实 AI 接入

接入 Playwright/spider-king、OpenHands SDK + Agent Server、隔离 worktree、代码生成和自动验证。此层产生真实候选采集器和候选 commit。

### 1.3 第三层：真实纠错闭环

人工运行后登记真实结果，平台生成 failure bundle，AI 进行可复现代码修复，回归测试通过后生成修复候选提交，人工再次运行并审查。

### 1.4 第四层：部署和长期维护

Linux Docker Compose、权限、备份、工具 profile、模型/提示词版本、运行手册、审计和资源预算齐全。

## 2. 阶段计划

| 阶段 | 主要产出 | 估算 |
| --- | --- | --- |
| 0. 方案冻结 | 仓库边界、ID 空值语义、状态和规则默认值 | 1–2 天 |
| 1. 项目骨架 | FastAPI、React、MySQL、Redis、Alembic、Compose | 2–4 天 |
| 2. 数据与 API | Pydantic、数据库表、鉴权、任务/报告/审查接口 | 3–5 天 |
| 3. 工作流 | LangGraph 节点、持久 checkpointer、Celery 任务、人工中断 | 4–6 天 |
| 4. 分析与证据 | Playwright、工具 profile、脱敏、manifest、证据查看 | 3–5 天 |
| 5. OpenHands Agent 执行 | SDK gateway、worktree、沙箱、提示词、代码边界 | 4–6 天 |
| 6. 验证与汇报 | pytest、Ruff、契约/业务验证、报告规则版本 | 3–5 天 |
| 7. 人工闭环 | 运行包、审查页、失败包、修复和候选提交 | 4–6 天 |
| 8. 安全与部署 | 镜像、权限、网络、备份、日志、故障演练 | 3–5 天 |

在一名主要开发人员配合 AI 编程的条件下，完整第一版预计 4–6 周。环境、OpenHands Agent app-server、浏览器工具或 Git 权限需要申请时，日历时间会增加。

## 4. 测试和验收矩阵

### 4.1 任务与规则

| 编号 | 场景 | 期望 |
| --- | --- | --- |
| A01 | 提交 HTTPS 招聘入口 | 创建 task，两个 ID 为空，投递分析 |
| A02 | 批量提交相同 URL | 去重或标记重复，不重复创建有效任务 |
| A03 | 非 HTTP(S) URL | INVALID_ENTRY_URL，不出网 |
| A04 | 列表有效且有实习岗位 | 观察为 INTERNSHIPS_FOUND |
| A05 | 列表有效但当前为空 | 观察为 NO_JOBS_OBSERVED，不是 NO_JOB_LIST_FOUND |
| A06 | 有岗位但当前无实习匹配 | 观察为 NO_INTERNSHIPS_OBSERVED |
| A07 | 没有列表页面 | 观察为 NO_JOB_LIST_FOUND，保存检查范围 |
| A08 | 登录或验证码 | 观察为 ACCESS_RESTRICTED，不编造接口 |
| A09 | 分析工具不可用 | TOOL_UNAVAILABLE，不假装取证 |
| A10 | 规则发布后查看历史报告 | 历史报告仍使用原 policy_version |

### 4.2 OpenHands Agent 和 Git

| 编号 | 场景 | 期望 |
| --- | --- | --- |
| B01 | 生成 collector/config/test | 只修改 allowlist，产生 diff 摘要 |
| B02 | AI 写入 Cookie 或 Token | 脱敏检查阻断候选提交 |
| B03 | AI 修改验证器 | scope violation，转人工 |
| B04 | 测试失败但有失败夹具 | 可进入修复，不能报告通过 |
| B05 | 测试全通过 | 创建候选 commit，保存 SHA |
| B06 | 同平台并行修复 | 锁阻断后者，不覆盖 worktree |
| B07 | 重复 commit 请求 | 返回原提交，不产生第二个提交 |
| B08 | 请求合并主分支 | 单独管理员操作并审计，普通 worker 不执行 |

### 4.3 人工运行和纠错

| 编号 | 场景 | 期望 |
| --- | --- | --- |
| C01 | 登记候选 commit 的运行包 | 版本和 manifest 校验后等待审查 |
| C02 | 运行包缺脱敏 manifest | 拒绝导入，不触发修复 |
| C03 | 人工发现字段错误 | 生成 failure bundle，进入广义诊断 |
| C04 | 人工发现分页漏数 | AI 可修改代码/配置，回归后新候选 |
| C05 | 人工发现全职混入 | AI 可修改筛选，回归后重新审查 |
| C06 | 人工发现验证码 | 外部阻断，除非有代码修复证据 |
| C07 | 人工选择 PASS | 绑定当前 code_revision，登记 ADOPTED |
| C08 | 选择 BUSINESS_RULE_REVIEW | graph 暂停，等待结构化补充 |
| C09 | 修复三轮仍失败 | REPAIR_BUDGET_EXCEEDED，不标成功 |

### 4.4 安全

| 编号 | 场景 | 期望 |
| --- | --- | --- |
| S01 | reviewer 下载其他 task 证据 | 403，不泄露路径 |
| S02 | evidence 路径含 .. | 拒绝并记录安全事件 |
| S03 | 页面文本包含忽略规则指令 | 当作不可信岗位数据 |
| S04 | AI 读取生产 .env | 沙箱不挂载，任务失败并告警 |
| S05 | response 含敏感 header | 脱敏后才可持久化 |
| S06 | worker 被杀后重启 | 同 thread_id 恢复，不重复 commit |

## 5. 运行验收

### 5.1 开发环境

1. Docker Compose 成功启动 API、worker、MySQL、Redis 和前端。
2. Alembic 在空库和已有库完成迁移。
3. 浏览器打开任务页面并创建任务。
4. 使用离线分析 fixture 生成 PlatformSpec、报告和测试结果。
5. 使用 fake OpenHands gateway 生成固定 diff，验证 worktree 和 Git 提交。
6. 注入人工审查问题，生成 failure bundle。
7. fake repair gateway 返回修复 diff，回归通过并创建修复候选。
8. 重启 worker，使用同一 thread_id 恢复等待中的任务。

### 5.2 集成环境

至少准备三类已授权 fixture：

- 静态 HTML 岗位列表；
- JSON/REST 列表与详情；
- 动态页面加分页或 GraphQL 请求。

每类覆盖有岗位、空列表、详情字段缺失、筛选错误和访问受限中的至少两项。fixture 用于验证平台，不代表产品只支持三个网站。

### 5.3 交付完成标准

以下全部满足才称为第一版闭环完成：

- URL 可创建任务；
- 状态和报告可恢复；
- 自动验证区分观察事实和技术状态；
- 候选代码包含配置、测试和证据引用；
- 人工运行可登记 code_revision；
- 人工审查可触发广义代码修复；
- 修复新增 commit，不覆盖基线；
- 修复有回归测试和新报告；
- platform_id/entity_id 仍为空；
- 没有未经授权的主分支变更；
- 证据、日志、数据库和 Git 无敏感信息；
- 任务可以从失败、暂停和 worker 重启恢复。

## 6. 部署验收

- [ ] Linux 主机有非 root Docker 运行策略；
- [ ] MySQL、Redis、证据目录有备份和恢复演练；
- [ ] runner 不使用宿主 Docker socket；
- [ ] 出网 allowlist 和禁止网段规则已测试；
- [ ] OpenHands Agent runtime、Playwright、工具 profile 和 Python 依赖已锁定；
- [ ] Git 提交器没有共享分支写权限；
- [ ] 管理后台启用 HTTPS、会话安全和 CSRF；
- [ ] 日志脱敏测试通过；
- [ ] 数据库迁移和恢复演练完成；
- [ ] 队列、锁、磁盘、数据库连接和 AI 费用有指标；
- [ ] 手工运行、人工审查、修复和证据下载有操作手册。

## 7. 决策清单

以下事项不阻塞骨架开发，但在进入真实批量接入前必须由业务方确认：

| 事项 | 当前建议 | 影响 |
| --- | --- | --- |
| 没有实习岗位是否提交候选 | 可生成候选，但报告为观察范围内无实习 | 是否减少后续人工审查 |
| 没有岗位列表是否提交 | 默认不采纳 | 是否保留研究分支 |
| 候选 commit 是否推远程 | 默认本地 bundle/commit | Git 权限和审查流程 |
| 人工 PASS 的硬条件 | 标题、URL、实习类型、正文优先 | 审查表和业务测试 |
| 缺发布时间如何验收 | 保留岗位并标记缺失 | 报告和清洗 |
| 访问受限是否提供登录 | 默认不保存长期凭证 | runner 和合规边界 |
| 同公司多个入口如何归并 | 一个 platform_key，多任务多入口 | 任务和证据关系 |
| 修复轮次和费用预算 | 3 轮，超限转人工 | 吞吐和成本 |
| 清洗映射何时接入 | 采集验收后下游处理 | 正式写库适配层 |

决策发布后写入 policy_versions 或项目 ADR，并绑定新任务；不能只改前端文案。

## 8. 风险与时间判断

主要不确定性是 OpenHands Agent runner/app-server 的 Linux 部署、spider-king 的工具 profile、招聘站点访问条件和旧采集项目空 ID 兼容适配。阶段 1、4、5 要尽早做环境验证。

纯编码工作估算 20–31 个工作日；串行实施、环境申请和人工确认后，日历周期约 4–6 周。最小闭环工程验证可以在 5–7 个工作日完成，但不能替代完整平台验收。

若工具或模型服务不可用，报告必须区分“平台代码未完成”“执行环境未配置”“目标站点受限”，不能把三者都报告为采集器失败。
