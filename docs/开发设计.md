## 1. 产品目标与已确认范围

平台把招聘网站接入和维护变成可追踪的开发任务。用户提交一个或一批招聘页面链接，AI 完成网站分析、规范提取、采集代码开发、自动验证、接入汇报和候选提交。用户手动运行候选采集器并审查实际数据；结果正确则采纳该代码版本，有问题则将证据和反馈交回 AI 修复。

“自动维护”是由用户反馈、任务失败或验证失败触发的代码维护，不包含主动轮询招聘网站。平台运行状态和队列健康检查属于自身运维，不属于网站变化监控。

### 1.1 范围矩阵

| 内容 | 本期行为 | 确认来源 |
| --- | --- | --- |
| 输入招聘链接 | 支持单条、批量粘贴；公司名可选 | 用户希望快速上量 |
| AI 分析和开发 | 自动执行，包括页面/API、代码、配置和测试 | 已确认 |
| 自动验证后汇报 | 成功、零岗位、无法接入、预算用尽均汇报 | 用户补充要求 |
| 自动候选提交 | 技术验证通过后自动生成隔离候选 commit | 已确认 |
| 正式岗位采集 | 人工在独立环境启动，平台记录结果 | 已确认 |
| 人工审查 | 审查绑定实际运行的候选 commit | 已确认 |
| AI 纠错范围 | 代码、配置、请求、筛选、分页、兼容性等能解决的问题 | 用户最新修正 |
| 网站变化监控 | 不实现 | 已排除 |
| 每条岗位调用 AI 解析 | 不实现 | 已排除 |

本平台中的自动候选提交、隔离分支和广义代码修复，是本次新流程的授权范围。它不意味着当前聊天可以提交旧仓库，也不意味着 AI 可以修改共享历史、直接上线或填写虚假 ID。

### 1.2 延续的岗位数据规则

- 正式采集器使用纯 Python HTTP；浏览器只用于开发取证与有界验证。
- 每个平台独立的 `collectors/<key>.py` 和 `config/platforms/<key>.toml`，共享逻辑归公共模块。
- 采集器不写 SQL；数据仓储不发送招聘网站请求。
- 只收实习岗位。Early Career、Student、Campus 等分类不能直接等同于实习。
- 发布时间取不到就标记缺失；不得用采集时间冒充。
- `crawl_version` 保持 `v1.0.0`，另记录 code commit、spec、policy、prompt、环境版本。
- 原始业务响应脱敏后保留，必须能重放。Cookie、Authorization、CSRF、账号等不得入证据或 Git。
- 原有清洗内容、哈希、版本、去重、实体映射和同步规则继续由下游系统承担，本平台不重新定义。

## 2. 业务流程

### 2.1 接入与纠错闭环

~~~mermaid
flowchart TD
    A["提交招聘 URL 或批量链接"] --> B["建任务并分配独立工作区"]
    B --> C["网站分析和 HTTP 协议取证"]
    C --> D{"是否取得开发所需证据"}
    D -- 是 --> E["PlatformSpec 校验"]
    E --> F["生成采集器、配置、夹具"]
    F --> G["自动验证"]
    G --> H["生成接入汇报"]
    D -- 否 --> H
    H --> I{"根据证据与规则确定下一步"}
    I -- 可交付候选 --> J["自动候选提交"]
    I -- 代码可修复 --> K["AI 诊断与代码修复"]
    I -- 外部条件或待确认 --> L["汇报并保存等待状态"]
    J --> M["人工运行指定 commit 的采集器"]
    M --> N["登记运行结果并人工审查"]
    N -- 通过 --> O["采纳准确的候选版本"]
    N -- 有问题 --> P["反馈与失败纠错包"]
    P --> K
    K --> Q["回归验证并生成新汇报"]
    Q --> I
    L -- 人工补充条件后恢复 --> C
~~~

解析无异常但采集为零、字段错位、混入全职、分页漏数等都属于人工审查可以发现的问题。流程不得只由异常堆栈驱动。

每次自动运行都要留下报告：即使没有走到代码生成，也应输出分析结果和未完成原因。进程崩溃且无法调用 AI 时，由程序按已有证据生成确定性的中断报告。

### 2.2 用户操作步骤

1. 选择目标采集器仓库和批准的开发基线，粘贴一个或一批 URL。平台默认仓库可由管理员预设，因此日常只需 URL。
2. 后台生成独立任务，展示当前阶段、已取得证据、当前限制和下一步动作。
3. 自动完成分析、开发、验证和汇报；有可验证代码时产生候选提交。
4. 用户获取绑定 commit 的代码包或 Git bundle，在自己的采集环境手动运行。没有 Git 远程配置也能交付候选。
5. 上传或导入运行结果包；平台显示运行规模、字段样本、失败详情和代码版本。
6. 用户审查并选择通过、需要修复、需补条件、业务确认或拒绝。
7. 需要修复时 AI 自动处理并再交付；通过后将该 commit 登记为已采纳版本。

正式采集不是自动验证。自动验证只做有限网络请求和夹具重放；正式采集范围、时间和是否写业务库由人工运行命令控制。

## 3. 汇报模型与可配置规则

### 3.1 三个独立判断

| 维度 | 回答的问题 | 示例 |
| --- | --- | --- |
| 网站观察结果 | 实际看到了什么 | 有实习、公开列表零条、未找到列表、访问受限 |
| 技术验证结果 | 代码被验证到了什么程度 | 列表通过、详情未验证、分页只抽样、回归失败 |
| 流程动作 | 下一步要做什么 | 候选提交、自动修复、人工补充、等待审查 |

这三个维度分开存储。不能因为“没有岗位”把未测试的详情解析报告为通过，也不能把“有岗位”当成代码正确。

### 3.2 建议的观察分类

以下是供实现使用的枚举草案，**不是已经定稿的业务处置规则**。

| observation_code | 展示名称 | 最低证据 | 不可推出的结论 |
| --- | --- | --- | --- |
| INTERNSHIPS_FOUND | 已发现实习岗位 | 真实岗位和实习判定依据 | 不代表全站已采全 |
| NO_INTERNSHIPS_OBSERVED | 在检查范围内未发现实习 | 有效列表、检查范围、筛选条件 | 不代表公司永久没有实习 |
| NO_JOBS_OBSERVED | 在检查范围内暂无岗位 | 有效空响应或官网明确空态 | 不能用异常页或空 HTML 得出 |
| NO_JOB_LIST_FOUND | 未找到岗位列表入口 | 已检查链接和页面证据 | 不代表公司无招聘 |
| NON_LISTING_RECRUITMENT | 招聘介绍、邮箱或公告型入口 | 页面类型与说明 | 不应编造列表/API |
| DETAIL_UNAVAILABLE | 详情未取得 | 列表记录、详情请求结果 | 不等于“无岗位” |
| ACCESS_RESTRICTED | 访问条件受限 | 访问结果、重定向、限制描述 | 单个 403 不能断定代码无法解决 |
| INCONCLUSIVE | 证据不足 | 缺口、预算/范围限制 | 不得报告为确定无岗位 |

没有“实习分类入口”不单独阻断接入：岗位正文可能有实习证据。空列表、实习数、详情失败数都记录 `count_scope`，例如本页、已遍历分页、所选国家或全入口；未知总数用 `null`，不用 0。

### 3.3 技术结果与下一步

技术结果为 `PASS / PARTIAL / FAIL / NOT_RUN`。详情、分页、筛选、字段、离线测试、网络抽样分别存结果和证据，不只存一个布尔值。

`next_action` 建议枚举：

- `CREATE_CANDIDATE`：必要技术检查通过且规则允许交付。
- `AUTO_REPAIR`：有可复现证据和可修改范围，尝试纠错。
- `REQUEST_INPUT`：缺访问条件、业务口径或修改范围。
- `WAIT_MANUAL_RUN` / `WAIT_REVIEW`：已交付候选。
- `CLOSE_WITH_REPORT`：用户拒绝或按发布规则结束。

没有岗位时允许生成分析报告或有限验证的代码，但不能伪造真实岗位测试成功。是否交付此类候选由规则决定；未配置时标注“待确认”，不自动采纳。

### 3.4 规则的编辑与发布

管理后台提供规则草稿、预览、发布和停用。数据库保存不可变版本、配置哈希、发布人和发布时间。新任务绑定发布版本；规则变更不改写历史报告。

第一版可配置项目：观察分类对应动作、最少样本数、分页覆盖要求、时间字段可缺失策略、零岗位/零实习处置、人工审查字段、修复预算。核心约束如“不伪造数据”“人工审查绑定 commit”“未验证不能填 PASS”不允许由业务规则关闭。

规则以有限条件 DSL 表达，Pydantic 校验；不接受用户上传 Python、JavaScript 或 SQL 作为规则。AI 可提出规则建议，不能自行发布。

### 3.5 单公司汇报与批量汇总

单公司汇报包含：输入/最终 URL、公司名是否确认、检查范围、观察结论、每项证据、规范版本、代码文件、验证结果、岗位计数、缺失字段、未验证项、可修复性、下一步、耗时及可获得的模型用量。

批量汇总按 observation、技术结果和下一步分别计数。一个失败公司不阻断其他公司；报告可筛选、下载 Markdown/JSON。本期站内展示状态，不主动发送邮件或聊天消息。

### 5.1 三类代码分离

| 仓库/目录 | 内容 | AI 自动写入策略 |
| --- | --- | --- |
| Auto_spider 控制面仓库 | 后台、工作流、验证框架、权限、部署 | 普通平台接入任务只读 |
| collector-catalog 采集器仓库 | 公共采集运行时、独立平台适配器、TOML、测试 | 任务按文件范围修改候选副本 |
| evidence/workspaces 数据目录 | 响应、报告、日志、运行包 | 不作为源码入 Git，按任务隔离 |

这使大量平台接入不会不断改动后台服务。AI 维护控制面或公共运行时也可以进入“框架维护任务”，使用更完整的回归范围与人工代码审查；业务接入失败不能悄悄改坏控制面让测试通过。

### 5.2 工作流与队列

LangGraph 是业务步骤的唯一路由；Celery 只负责排队、执行与恢复投递，不再维护另一套业务状态机。MySQL 是持久状态来源，Redis 不是长期报告库。

工作流必须有持久 checkpointer。选择 MySQL 意味着需要实现并验证适配器，不能假设官方自带可直接使用的 MySQLSaver。此项列为首阶段集成门槛，细节见运行规范。[LangGraph 持久化接口](https://docs.langchain.com/oss/python/langgraph/checkpointers)

### 5.3 网站分析工具与 skill

spider-king 是可版本化的执行说明与工具路由，不是拷贝 SKILL.md 就能独立运行的浏览器服务。构建 runner 镜像时显式打包已批准的 skill 及所需脚本，配置其 MCP/HTTP 工具地址并做能力自检。

现有 Windows 下工具路径不可硬编码到 Linux。平台保存 `tool_profile` 和 `skill_bundle_hash`；Playwright、网络观察、调试、离线分析等能力逐项标注 available/unavailable。缺工具要产生具体报告，不能假装完成取证。只装接入所需工具，不自动调用整套本机任意工具。

### 5.4 代码生成与确定性验证

AI 负责解释证据、编写代码和提出修复；平台程序负责校验 Schema、运行测试、判定命令退出码、检查 diff、计算文件哈希和生成 Git 提交。

AI 输出“通过”不能替代测试结果。生成代码不能自行改动受信验收器、网络策略、报告规则和 Git 提交器。岗位网页中的文字作为待分析数据，不能提升为执行权限或系统指令。

## 6. 采集契约与空编号方案

### 6.1 统一输出

采用 `CollectorRecord` 作为新平台开发与人工运行契约，尽量对齐现有 `RawJobRecord` 的 `job / source_payload / collection / validation / availability / error` 结构，同时新增稳定 `platform_key`，允许业务编号缺失。

元数据接口中 `platform_id=null`、`entity_id=null`；兼容记录的 `source_platform=null`。TOML 无 null 值，模板直接省略两项，由新配置加载器返回 None，不能写 `platform_id = null`。

岗位必需项为稳定 source_id、source_url、source_name、title，以及 description/requirements 至少一项有有效正文。两段原站混排时记录 `section_split_status`，不能虚构切分结果；保留原始业务片段供重放。

发布时间保留原始值和时区依据，新记录可用 null 表示未知；未来转换旧原始库时才按约定写 0，并标记缺失。没有发布时间默认保留，只有显式参数才跳过。

### 6.2 现有项目真实约束

本次只读核对得到：

| 位置（旧项目相对路径） | 已观察行为 | 对新设计的影响 |
| --- | --- | --- |
| config/platforms.py | 对 TOML 的 platform_id 执行 int(...) | 旧加载器无法读取省略编号的新配置 |
| models/raw_job.py | RawJobRecord.validate 要求 source_platform 非空 | 不能把空编号声称为旧记录完整有效 |
| collectors/base.py | 把 platform_id 赋给 source_platform | 需要明确的新运行时或兼容适配层 |
| services/crawler_service.py | 写库前过滤缺 source_platform 的记录 | 直接套旧命令可能导致零写入 |

因此第一版采用新的候选采集运行时，允许空编号完成开发、验证、手动全量采集和结果审查。旧爬虫项目和库结构不在本次文档任务中修改。

### 6.3 人工运行与下游写库

人工命令的默认 `review` 模式将真实采集结果保存为采集暂存和审查产物，管理库只记运行元数据和文件索引。新平台的目标链路是：

`采集器 → 允许空 ID 的采集暂存 → 人工审查 → 清洗映射 → 原始库/清洗库`。

因此 `platform_id`、`entity_id` 在采集、验证、候选提交、人工运行和人工采纳阶段都保持 `NULL`。清洗服务在读取采集暂存后，分别补充平台业务编号和公司实体编号。

现有旧原始库的 `source_platform` 非空约束只作为兼容风险记录，不作为新平台接入前置条件。若未来要把空 ID 的采集暂存桥接到旧原始表，应新增明确的映射适配器或暂存表迁移，并在映射缺失时返回 `PLATFORM_MAPPING_REQUIRED`；不能把这个错误变成 0、随机数或静默丢弃。当前“编号先不管”的需求不会阻断本平台的代码开发、人工运行和清洗前的数据交付。

### 6.4 兼容语义

业务哈希沿用 `MD5(normalize_text(title) + "\n" + normalize_text(description) + "\n" + normalize_text(requirements))`。证据文件完整性使用 SHA-256，两者用途不同。

失败详情保存独立失败信息，不能覆盖最近成功内容；同一来源以 platform_key/source_id 识别，新记录进入旧系统后由 source_platform/source_id 识别。跨来源业务去重仍交原系统处理，不擅自改索引，也不运行历史全局哈希唯一迁移。

人工审查按 `review` 模式采集时展示错误条目，但错误条目不算有效岗位。后续业务库的 clean_status 和 sync_status 与本平台 task_state、review_result 完全分离。

## 7. 失败诊断和维护边界

### 7.1 根据可解决性分流

| 示例 | 初始处理 | 满足什么条件转 AI 修复 |
| --- | --- | --- |
| 无异常但列表为零 | 对比网页与请求范围 | 存在错误筛选、分页、参数等证据 |
| 字段内容错或混入全职 | 对比来源与契约 | 可以修正映射、正文解析或筛选 |
| 403、TLS、超时 | 记录现场并有界复现 | 请求实现、证书配置、连接管理等代码因素可修 |
| 站点无公开列表 | 汇报已检查范围 | 找到新的公开入口或可复现数据接口 |
| 账号或业务权限不足 | 请求人工提供访问条件 | 条件满足后重新验证 |
| 依赖缺失、SDK 兼容问题 | 判断任务环境与锁版本 | 已批准依赖调整且能重建测试 |
| 公共适配器 bug | 关联受影响平台 | 建框架维护任务，扩大回归范围 |

不按错误名称永久排除网络类问题。AI 必须给出根因、证据、修改点和验证方式；不能通过关闭 TLS 校验、隐藏错误、清空结果或降低验收要求来“修好”任务。

### 7.2 纠错包

除堆栈外，包含候选 commit、基线、运行参数、过滤条件、检查范围、期望/实际字段、错误样本、正确对照、脱敏响应、时间、环境指纹、人工说明和 issue_id。零结果允许没有岗位样本，但要有入口与响应证据。

缺复现证据时 AI 先在预算内补充取证；仍无法判断则请求用户输入。达到修复轮次或资源预算后汇报具体卡点，不无限循环、不把未解决任务标为成功。

### 7.3 平台自身维护

管理员可创建 `FRAMEWORK_MAINTENANCE` 任务维护后台、公共采集器、工具镜像或测试框架。它使用独立仓库范围和验收计划，不能由普通网页内容或 AI 自行提升权限产生。平台通过候选版本和人工审查升级，正在运行的任务继续使用原锁定版本。

## 9. 权限、证据与运行安全

角色为 operator（提交/导入）、reviewer（审查/采纳）、maintainer（修复/恢复）、admin（规则与仓库设置）。同一人可以拥有多个角色，首版不强制双人审批。

部署为内部管理系统：本地用户、禁公开注册、密码哈希、HttpOnly/Secure 会话 cookie、CSRF 校验、角色与资源级权限检查。证据只经鉴权 API 下载，不暴露目录路径。外部 HTML 以纯文本或受限预览展示，不能以后台同源直接执行。

URL、重定向、子资源和生成代码的网络出口都必须限制内网、回环、云元数据与非 HTTP(S) 目标；允许公开招聘域名及经取证发现的必要 ATS 域名。限制要由网络层执行，不能只检查前端输入。模型服务、招聘网站、依赖构建分别使用受控出口。

AI 容器不持有管理库/业务库凭据、生产 Git 写凭据、宿主 Docker socket。普通 subprocess 或 SDK workspace_write 本身不是完整隔离。具体容器、Git 提交和重试设计见运行规范。

证据落盘前按白名单抽取业务内容并脱敏，保存 SHA-256 和关联对象；完整原始 HAR 不直接进入持久目录。必要会话凭据只短期驻留运行时，不写入 report/spec/fixture。响应中业务字段名如 job_token 需按用途区分，不能盲删造成不可重放。

## 10. 可交付成果与完成标准

每个任务至少交付一份报告；具备条件时另外交付规范、采集器、配置、夹具、验证记录和候选代码包。每次修复形成新轮次和新报告，旧证据与旧审查保留。

“已采纳”只表示人工认可特定 commit 的采集结果。它不代表已经合入旧项目、已经推送远程、已经入原始库或已经同步下游。管理后台分别展示 adoption、integration、delivery、downstream_mapping 状态。

完整产品的实施阶段、关键技术验证和验收矩阵见 [开发计划与验收](开发计划与验收.md)。首版按完整闭环建设，分阶段实现不等于缩减成几个站点的演示系统。
