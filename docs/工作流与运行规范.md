# 工作流与运行规范

本文档定义 LangGraph、Celery、Codex、Playwright、Git 和人工操作之间的执行顺序。目标是让长任务可恢复、代码可审查、失败可重现，且正式采集始终由人工发起。

## 1. 运行生命周期

~~~mermaid
sequenceDiagram
    actor User as 操作人
    participant API as FastAPI
    participant DB as MySQL
    participant Queue as Celery/Redis
    participant Graph as LangGraph
    participant Agent as Codex Runner
    participant Browser as Playwright 分析器
    participant Git as 受信 Git 提交器

    User->>API: 提交 URL
    API->>DB: 创建 task、event、checkpoint
    API->>Queue: 投递 onboarding job
    Queue->>Graph: 启动 thread
    Graph->>Browser: 分析页面和网络请求
    Browser-->>Graph: 脱敏证据
    Graph->>Agent: 生成 spec、代码和测试
    Agent-->>Graph: diff、测试输出和说明
    Graph->>DB: 保存验证与报告
    Graph->>Git: 创建候选 commit
    Git-->>DB: 返回 branch、commit 和文件清单
    User->>API: 登记人工运行结果
    API->>DB: 创建 manual run
    User->>API: 提交 PASS 或问题
    API->>Queue: 投递修复任务
    Queue->>Graph: 恢复原 thread
    Graph->>Agent: 读取 failure bundle
    Agent-->>Graph: 修复 diff 和回归结果
    Graph->>Git: 创建修复候选 commit
    Graph->>DB: 保存报告并等待下一次人工运行
~~~

## 2. LangGraph 图

### 2.1 节点和转换

| 节点 | 输入 | 输出 | 失败去向 |
| --- | --- | --- | --- |
| `normalize_input` | URL、请求人、策略版本 | task、platform_key、目标仓库 | `INVALID_ENTRY_URL` |
| `acquire_lock` | task、platform_key | 任务锁 | `CONFLICTING_RUN` |
| `inspect_site` | 入口 URL、tool profile | 页面/API 证据 | `ANALYSIS_NO_EVIDENCE` |
| `build_spec` | 证据 | PlatformSpec | `SPEC_INVALID` |
| `prepare_worktree` | task、基线 commit | worktree | `WORKTREE_FAILED` |
| `generate_code` | spec、模板、证据 | diff、测试夹具 | `CODE_GENERATION_FAILED` |
| `run_validation` | worktree、测试配置 | 分层结果 | `VALIDATION_FAILED` |
| `build_report` | 观察、技术结果、证据 | report | `REPORT_FAILED` |
| `report_gate` | report、policy | 下一动作 | `REQUEST_INPUT` 或候选 |
| `commit_candidate` | 已验证 diff | commit record | `GIT_COMMIT_FAILED` |
| `await_manual_run` | candidate | interrupt | 人工恢复 |
| `ingest_manual_run` | manifest、commit | manual run | `ARTIFACT_INVALID` |
| `record_review` | 审查结果 | review record | `REVIEW_INVALID` |
| `build_failure_bundle` | review、运行证据 | failure bundle | `BUNDLE_FAILED` |
| `diagnose_failure` | failure bundle、代码 | diagnosis | `REQUEST_INPUT` |
| `patch_code` | diagnosis、白名单 | 修复 diff | `CODE_SCOPE_VIOLATION` |
| `run_regression` | 修复 diff | 回归结果 | 再诊断或人工 |
| `submit_fix` | 回归通过的 diff | 修复候选 commit | `GIT_COMMIT_FAILED` |
| `release_lock` | task、run | 锁释放 | 告警但不改结论 |

### 2.2 人工中断

在 `report_gate`、`await_manual_run`、`record_review`、`diagnose_failure` 的信息不足分支调用 LangGraph interrupt。每次中断保存：

- thread_id；
- checkpoint revision；
- 展示给人的 JSON 载荷；
- 允许的 resume schema；
- 调用人和时间；
- 当前 task 与 run。

恢复必须使用同一 thread_id 和幂等键。前端不能把任意 JSON 直接写进 graph state；API 先通过 Pydantic 校验，再把有限字段作为 resume 输入。

生产环境不能使用只在内存中的 checkpointer。MySQL 是本项目既定元数据数据库，首阶段需要实现并测试一个持久 checkpointer adapter，或明确配置经批准的持久组件；未完成前不得把重启后的任务宣称为可恢复。

### 2.3 状态锁和并发

同一个 `platform_key` 同时只允许一项会改变候选代码的任务。以下操作共享锁：

- 生成代码；
- 代码修复；
- 候选提交；
- 变更受信公共适配器。

只读报告、下载证据和人工审查可并行。数据库锁、Redis 锁和 worktree 目录都要有租约与 owner；超时只允许恢复器清理明确过期的锁。

## 3. Celery 运行规则

### 3.1 队列

| 队列 | 任务 | 并发建议 |
| --- | --- | --- |
| `analysis` | Playwright、协议分析和证据整理 | 低并发，按域名限速 |
| `coding` | Codex 生成和修复 | 每个 runner 一个隔离容器 |
| `validation` | pytest、Ruff、契约和业务检查 | 可水平扩展 |
| `reporting` | 报告渲染、批量汇总、文件哈希 | 普通并发 |
| `maintenance` | 镜像、工具、公共框架维护 | 单独权限和队列 |

正式采集没有 Celery 任务。人工启动采集器后，平台只接收运行包或由操作者显式登记运行。

### 3.2 幂等和重试

任务参数包含 `task_id`、`run_id`、`code_revision`、`policy_version`。Celery 重投只重复执行没有完成的阶段，不能重复 commit 或报告。

可重试：runner 短暂退出、Playwright 初始化失败、模型临时失败、Redis 短暂失败和证据写入临时失败。

需人工：访问受限、代码白名单失败、业务规则不清、达到修复预算和 Git 分支被外部改动。

任务设置明确时间限制、最大输出字节数、最大修复轮数。Redis 只存 broker/result 短期状态，MySQL 持久保存工作流记录。长时间任务显式设置 visibility timeout，避免重复执行。

## 4. Codex Runner

### 4.1 Gateway

后端不直接在 HTTP 进程创建 Codex。Celery 任务调用 `CodingAgentGateway`，由它：

1. 校验任务和工作区；
2. 准备最小输入包；
3. 创建或恢复 Codex thread；
4. 设置 sandbox 和环境变量；
5. 传递系统约束、证据和检查命令；
6. 收集 streamed events、最终说明、修改文件和退出结果；
7. 执行平台确定性验证；
8. 将摘要和完整日志分开落盘。

### 4.2 Python SDK 接入

官方 Python SDK 的基本形式：

~~~python
from openai_codex import Codex, Sandbox


def run_agent(prompt: str) -> str:
    with Codex() as codex:
        thread = codex.thread_start(
            model="gpt-6-sol",
            sandbox=Sandbox.workspace_write,
        )
        result = thread.run(prompt)
        return result.final_response
~~~

安装包为 `openai-codex`，要求 Python 3.10 或更高版本。生产镜像锁定包、Codex CLI runtime、模型、提示词包和配置，不依赖 `pip install latest` 的隐式变化。不要把普通 `openai` 客户端当成受限代码执行 SDK。

### 4.3 Prompt 输入契约

Prompt 由服务端结构化拼接：

- 任务目标和阶段；
- PlatformSpec 或 failure bundle；
- 当前基线 commit；
- 允许读取/修改的相对路径；
- 必须运行的命令及超时；
- 不得读取的目录和敏感数据策略；
- 现有采集契约；
- 输出格式：改动摘要、测试结果、无法修复原因、后续建议。

网页和接口证据包标记为不可信数据。网页文字只能作为岗位数据和分析证据，不能覆盖系统规则、调用额外工具、泄露密钥或修改允许范围。

### 4.4 沙箱

默认 `Sandbox.workspace_write`；review 节点用 `Sandbox.read_only`。容器：

- 只挂载任务 worktree、输入证据和临时输出；
- 不挂载生产数据库和宿主 Docker socket；
- 网络出口按阶段限制；
- shell 程序和参数受白名单/策略控制；
- 内存、CPU、磁盘、进程、网络响应和总时间受限；
- 任务结束保存差异与日志，再销毁容器。

Codex 的 sandbox 是权限设置，不替代容器、网络和凭证隔离。不能因为 SDK 传入 workspace_write 就认为任务已经安全隔离。

## 5. 网站分析与证据

### 5.1 分析阶段

Playwright 记录：

- 最终 URL、状态码、标题；
- 页面重要请求；
- XHR、Fetch、GraphQL 请求方法、URL、参数和响应摘要；
- 岗位链接；
- 分页、筛选和详情点击行为；
- 页面截图和必要 DOM 片段。

spider-king 和其他工具作为任务 profile 的能力来源。每个 profile 声明工具版本和可用能力；工具不可用时进入 `TOOL_UNAVAILABLE`，不能让 AI 根据猜测生成代码。

### 5.2 脱敏

响应头只保留白名单，Cookie、Authorization、Set-Cookie、CSRF 和会话 ID 全部删除。URL 查询参数按 secret、key、token、code、session、password 等规则脱敏；正文发现疑似令牌时，保存清洗版本并记录命中位置。

证据写入后计算 SHA-256，manifest 也做哈希。完整 HAR 不直接进入持久目录；长正文分片并设置大小上限。

### 5.3 HTTP 复现

浏览器捕获请求由 AI 分析后改写为确定性 HTTP 请求。正式采集器不能复制动态用户 Cookie；需要 token 的接口进入访问阻断，除非用户提供已批准的短期人工运行凭据并说明存储方式。

分析阶段只确认列表、详情、分页、时间和实习筛选证据，不采集全量岗位。验证采样上限由 policy 控制，正式全量由人工命令决定。

## 6. 采集器生成规范

### 6.1 文件范围

普通任务只允许修改：

~~~text
collectors/<platform_key>.py
config/platforms/<platform_key>.toml
tests/fixtures/<platform_key>/**
tests/test_<platform_key>.py
docs/generated/<platform_key>.md
~~~

配置 TOML 不写 `platform_id` 或 `entity_id`，除非任务已经绑定业务映射并由管理员明确授权。缺失字段由 loader 返回 None。

### 6.2 代码契约

采集器必须：

- 实现基类规定的 collect/list/detail 方法；
- 为列表、详情、分页和字段转换写可重放测试；
- 使用统一超时、重试、限速和错误对象；
- 保留上一次成功详情，不被失败响应覆盖；
- 对空结果和下架状态显式标记；
- 脱敏请求轨迹；
- 把正文转换为可清洗的纯文本；
- 不写 SQL、不访问 MySQL、不调用 Codex；
- 不把浏览器启动逻辑放入正式运行路径。

### 6.3 生成前后检查

生成前检查公共接口和目标基线；生成后执行：

1. `git diff --name-only` 路径检查；
2. AST 扫描禁止数据库连接、秘密常量和未批准 import；
3. `python -m compileall`；
4. Ruff；
5. 采集契约；
6. 夹具回归；
7. 业务验收；
8. 人工查看 diff 摘要；
9. 受信提交器创建 commit。

禁止 AI 只修改测试以消除失败而不说明业务理由。测试规则和验证器属于受信代码。

## 7. 人工运行和审查

### 7.1 运行包

人工运行程序输出 manifest，包含：

- code_revision、platform_key、crawl_version；
- 运行命令和参数；
- 环境 fingerprint；
- 开始/结束时间；
- 列表请求和详情请求统计；
- 有效、失败、过滤、重复岗位计数；
- 样本和错误证据路径；
- 是否写正式库、写入目标和结果；
- 脱敏状态。

建议提供 `preview` 和 `production` 两个 profile。preview 只写运行包；正式业务写库由既有采集程序和人工命令控制。没有正式写库也可以完成代码审查。

### 7.2 审查清单

审查人检查：

- 入口和详情 URL；
- 实习过滤；
- 岗位标题和 source_id；
- 地点、描述、要求；
- 发布时间缺失标记；
- 详情链接可访问性；
- 分页和总数范围；
- 重复、全职、校招混入；
- 失败岗位是否覆盖旧成功详情；
- 证据、日志和输出是否脱敏。

点击 PASS 前必须绑定审查所看的 code_revision。审查不能把后续新 commit 自动标为通过。

## 8. 失败纠错循环

~~~mermaid
stateDiagram-v2
    [*] --> ReviewFailed
    ReviewFailed --> BundleCreated: 保存运行包和人工意见
    BundleCreated --> Diagnosing
    Diagnosing --> NeedInput: 证据不足或业务不明
    Diagnosing --> ExternalBlocked: 代码无法解决
    Diagnosing --> Patching: 存在可验证代码或配置修复
    Patching --> Regression
    Regression --> Patching: 修复测试失败且仍在预算内
    Regression --> CandidateFix: 回归通过
    Regression --> NeedInput: 超预算或修改范围扩大
    CandidateFix --> ManualRun: 等待人工重新运行
    ManualRun --> ReviewFailed
    NeedInput --> [*]
    ExternalBlocked --> [*]
~~~

诊断结果至少包含根因假设及证据、代码可修复性、预计修改文件、不修改的部分、测试计划、风险和修复预算。

代码可解决包括请求构造、参数、headers、分页、选择器、JSON 路径、日期、筛选、正文清洗、状态和配置，不限于 parser 函数。无法通过代码解决才进外部阻断；网络类问题仍可在证据充分时尝试低风险代码调整。

修复生成新 commit，不覆盖原候选。回归包括旧夹具、新失败夹具和跨平台契约测试。修复后重新生成报告，回到人工运行而不是自动写生产库。

## 9. Git 运行规范

### 9.1 Worktree

每任务从管理员配置的基线 commit 创建 worktree：

~~~text
/srv/auto_spider/worktrees/<task_id>/<run_id>/
~~~

同一平台只允许一个写入 worktree；分析只读可以使用临时副本。任务失败不删除 worktree，直到报告、diff 和日志归档完成。

### 9.2 分支和提交

~~~text
ai/onboarding/<platform_key>/<task_id>
ai/repair/<platform_key>/<task_id>-r<attempt>
~~~

提交格式：

~~~text
feat(collectors): 接入 <platform_key> 招聘岗位采集
fix(<platform_key>): 修复岗位字段提取
~~~

提交前由受信提交器检查分支、diff 文件清单、敏感信息、测试、commit message 和证据关联。系统不执行 force push、删除远程分支、reset --hard、共享历史 rebase 或主分支自动合并。远程推送作为单独管理员配置；默认使用本地 bundle/commit 交付。

## 10. 服务运行和排障

目标启动顺序：

~~~bash
docker compose up -d mysql redis
alembic upgrade head
uvicorn auto_spider.api.main:app
celery -A auto_spider.workers.celery_app worker -Q analysis,coding,validation,reporting
cd apps/frontend && npm run dev
~~~

实际命令以实现后的 pyproject、Compose 和 Makefile 为准。这里是目标接口，不表示当前目录已经可以执行。

排障顺序：

1. 查看 task、run 和 event 状态；
2. 查看 runner 和 Celery 日志；
3. 检查 worktree、manifest 和证据权限；
4. 校验 code/spec/policy/environment 版本；
5. 重放离线 fixture；
6. 证据充分时再进行有限网络分析；
7. 用 retry/resume，不直接手改数据库状态。

正式采集运行时不要清理 worktree、重启相关 worker 或覆盖证据。排查只读日志和任务状态。

## 11. 可观测性和安全事件

日志字段包含 `request_id`、`task_id`、`run_id`、`platform_key`、`workflow_node`、`code_revision`、`model`、`tool_profile`、耗时和 outcome；敏感信息先脱敏。

指标包括阶段耗时、成功率、AI 运行次数和费用、自动修复成功率、人工 PASS 率、观察分类、工具不可用、访问阻断、队列堆积、磁盘和数据库状态。

发现 Cookie、Token、生产凭证或个人信息进入证据/Git：

1. 阻止候选提交；
2. 标记安全事件并限制下载；
3. 删除工作区泄露文件但保留审计事件；
4. 按仓库策略轮换凭证；
5. 清理 Git/证据并重新脱敏检查；
6. 管理员确认后再继续任务。

不能把敏感信息泄露当成普通解析问题自动提交。
